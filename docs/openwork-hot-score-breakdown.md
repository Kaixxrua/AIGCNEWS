## 三、规模校正增长：100 分，贡献 55 分

这一项衡量新增 stars 相对于仓库已有规模是否显著。

公式：

```text
规模原始值 = ln(1 + 今日增长 / sqrt(昨日 stars))
```

代入：

```text
今日增长 = 568
昨日 stars = 17,565
sqrt(17,565) ≈ 132.53
568 / 132.53 ≈ 4.285
```

因此：

```text
规模原始值 = ln(1 + 4.285)
             = ln(5.285)
```

固定参考上限是：

```text
ln(1 + 4) = ln(5)
```

因为 `ln(5.285)` 已超过 `ln(5)`，所以分项封顶：

```text
规模校正增长分 = 100
```

对最终热度的贡献：

```text
100 × 55% = 55
```

## 八、Watchers 数据 Bug

GitHub REST 返回两个容易混淆的字段：

| GitHub 字段 | 实际含义 |
| --- | --- |
| `watchers_count` | 历史兼容字段，实际等同于 stars |
| `subscribers_count` | 真正订阅仓库通知的用户数 |

当前 REST 采集代码错误地把 `watchers_count` 写入内部 `watchers` 字段。

污染数据的明显证据：

```text
2026-07-29：
stars    = 17,565
watchers = 17,565
```

两者完全相等，是因为 stars 被重复写入 watchers。

系统随后计算：

```text
17,769 - 17,565 = 204 watcher 增长
```

于是算法误认为该仓库一天新增了 204 个通知订阅者，并把社区项推到 100 分。

此外，数据库快照和候选表对 watcher 使用了 `GREATEST` 更新方式。污染值通常接近 stars，远大于真实 subscribers，因此后续即使抓到正确的较小值，也无法覆盖污染值。

### 修正后的合理区间

如果完全不计算社区项：

```text
99.1824 - 5 = 94.1824
```

如果只保留可信的 `+28 forks`，忽略 watcher 增长，社区分约为 54.19，贡献约 2.71：

```text
94.1824 + 2.7096 ≈ 96.8920
```

因此 watcher 数据 Bug 大约造成了 `2.29～5` 分的不当增益，但不是总分接近 100 的主要原因。

## 十、问题归因

### 1. 数据完整性问题

必须修复：

- REST 采集改用 `subscribers_count`；
- GraphQL 继续使用 `watchers.totalCount`；
- Search/Trending 没有 subscriber 数据时标记为社区指标不完整；
- 允许新的权威 subscriber 值降低并覆盖历史污染值；
- 将不可恢复的历史污染快照标记为不完整，不用今天的数据伪造历史；
- 清除受污染日指标中的社区贡献并重建热度。

### 2. 评分模型校准问题

需要单独决定：

- 规模校正增长、增长加速度和绝对增长都在奖励 stars 增长；
- 三项合计占总热度 85%；
- 对爆发项目，规模分和加速度分可能同时封顶；
- `openwork` 在不计算社区项时仍有 `94.1824`。

如果产品预期是“这种增长不应达到 90 分以上”，则需要单独设计 `daily_hot_v6`，调整增长类分项的重复奖励、权重或封顶方式，而不是把该变化混进 watcher 数据修复。
