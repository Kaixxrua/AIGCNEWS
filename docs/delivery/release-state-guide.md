# 发布候选承接与健康门禁

本文依据[本地交付控制器](../local-delivery.md)，仅概述既有发布与承接语义。

## 候选选择与承接

- 部署仅选择最新已验证的 local main；已开始的候选不中断。落地前须再次核对 base 和 head，不能把旧验证套到新提交。
- 每个 branch+SHA 单独记录交付，精确 SHA 的 CI 回执保存在 `runs/<id>/ci.json`。CI、landing、release、mirror 分别使用进程锁。
- 发布失败只通知精确 release SHA 对应的承接任务。新 AO 任务在 `dev_session.start` 时核对 provider thread ID 并激活绑定；未知归属不猜测，旧任务不按标题推断绑定。有 AO 绑定时不跨通道回退。

详见原文[权威与隔离](../local-delivery.md#权威与隔离)和[开发任务的停止边界](../local-delivery.md#开发任务的停止边界)。

## 健康门禁与发布状态

- 发布复用 `deploy_production.py` 的生产主机锁、digest、迁移、探针和所有权回滚，以及既有公网边缘制品发布流程。
- 失败、控制器中断或回执缺失均不放行；失败发布不自动无限重试。
- `release=delivered` 表示源站与边缘均发布成功。验收依据生产 active SHA、edge-state 和公开端点；不能把已交接表述为已上线。
- GitHub 仅作异步镜像，同步失败记录为 pending，不决定生产进度；远端分叉须报告，不能强推覆盖。

详见原文[权威与隔离](../local-delivery.md#权威与隔离)和[切换步骤与恢复](../local-delivery.md#切换步骤与恢复)。

## 开发任务何时结束

本地影响面验证通过并提交、推送后，只有精确 SHA 已入队、创建时归属一致，且通知控制器在最近 120 秒核实唤醒通道，Stop hook 才允许按交接边界结束，无须等待 CI、合并或发布完成。推送失败、归属未知、通道未就绪或已有待修复失败，均不能冒充交接成功。

成功只更新看板，失败才唤醒；修复提交后再次交接。发送超时记为 unconfirmed，不盲目重发。真实的已上线生产证据仍可作为终态放行依据；基础设施修复的显式全链路验收要求保持。

详见原文[开发任务的停止边界](../local-delivery.md#开发任务的停止边界)。
