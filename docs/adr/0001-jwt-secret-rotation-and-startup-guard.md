# ADR 0001：JWT 密钥轮换与启动守卫

- 状态：Accepted
- 日期：2026-08-03
- 关联提交：`447dae0` `fix(auth)!: JWT 密钥缺失或公开时拒绝启动并轮换生产密钥`

## 背景（Context）

2026-08-03 的五维评估确认一处致命问题：生产 `.env` 中的 `JWT_SECRET_KEY` 与仓库公开的
`.env.example` 默认值逐字相同（经哈希比对证实，未打印密钥值）。由于 JWT 签名密钥是签发
`/api/ops/*` 管理令牌的唯一凭据，任何读过公开示例配置的人都可以在本地伪造 admin JWT，
完全接管运维端点。

同时，`config.py` 中的默认值本身即是"已知公开值"：即使运维者忘记配置，应用也会带着一个
对全世界公开的签名密钥正常启动，且无任何告警。

## 决策（Decision）

1. **移除默认密钥**：`JWT_SECRET_KEY` 在 `backend/app/core/config.py` 中的默认值改为空串。
2. **启动守卫**：`backend/app/main.py` lifespan 启动阶段校验密钥——为空、或等于任何已知
   历史公开默认值时，拒绝启动并在日志中给出生成指引（`openssl rand -hex 32`）。宁可使
   部署失败，也不带着公开密钥运行。
3. **轮换生产密钥**：生成 64 字符随机密钥写入 `.env`（全程不打印值，仅以 sha256 哈希比对
   确认变更），通过 `scripts/manage_main_stack.sh up` 重启栈生效。
4. **示例配置占位符化**：`.env.example` 中的密钥项改为占位符 + 生成指引注释，不再携带
   任何可用值。

## 备选方案（Alternatives considered）

- **密钥管理服务 / 文件挂载（Docker secret）**：对当前单节点自托管部署属于过度工程；
  `.env` 已是既有的秘密分发通道，文件权限（600）由部署脚本保证。多节点化时再重议。
- **运行时热轮换（双密钥并存验证）**：签发/验证双密钥列表可以免登出轮换，但显著增加
  签发与验证路径复杂度。当前规模下"轮换即全员重新登录"（中断数秒）是可接受代价，
  已获项目所有者批准。

## 后果（Consequences）

- 正面：公开默认值再也无法用于伪造令牌；遗忘配置从"静默裸奔"变为"响亮失败"；示例配置
  不再泄漏可用秘密。
- 代价：每次轮换会使全部已签发 JWT 失效（所有用户重新登录）；守卫使 CI/新环境必须显式
  生成密钥（已在测试与文档中固化指引）。
- 已知权衡：`ACCESS_TOKEN_EXPIRE_MINUTES` 仍为 7 天且无吊销列表——轮换是唯一的全网
  吊销手段。缩短有效期会增加登录频率，如需调整应单独决策。

## 验证（Verification）

- 契约测试：默认/公开值 → 启动失败；随机值 → 正常启动（`backend/tests/`）。
- 运行时验证：轮换后旧 token 访问受保护端点返回 401，重新登录流程正常，
  `/api/ready` 健康。
