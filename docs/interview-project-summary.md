# AIGC_NEWS 面试答辩项目概括

## 项目一句话介绍

**AIGC_NEWS** 是一个面向 AI 从业者的“**AIGC 资讯聚合 + 智能检索问答 + 自动简报生成**”平台，把分散在多个站点的 AI 论文、开源项目、科技新闻和社区热点，统一采集、清洗、索引、排行、问答和展示。

---

## 1. 项目是做什么的

这个项目解决的是 **AI 信息过载** 问题。

AI 领域每天都有大量新论文、新开源仓库、新产品和新资讯，用户如果分别去看 HuggingFace Papers、GitHub Trending、Techmeme、Product Hunt、Hacker News，信息获取成本很高，而且难以做横向比较和进一步追问。

所以这个项目做了三件事：

1. **把多源 AI 信息自动采集进来**；
2. **把信息变成可检索、可问答、可追踪的数据资产**；
3. **把“看资讯”升级为“问资讯、读论文、收简报”**。

从产品定位上，它不是一个单纯新闻站，而是一个 **AI 垂类情报平台**。

## 2. 功能模块总览表

| 模块 | 面向用户的价值 | 核心实现方式 |
|------|----------------|--------------|
| 多源资讯采集 | 自动汇总 AI 热点，减少用户分散浏览成本 | 5 路爬虫 + 异步编排 + 内容丰富 + 三库写入 |
| Dashboard 仪表盘 | 快速看当天热点、趋势和来源分布 | MySQL 排行快照 + Redis 缓存 + GitHub 热度算法 |
| RAG 智能问答 | 用户可以直接提问“今天有什么值得关注” | 混合检索 + 精排 + Tool Use + SSE 流式输出 |
| 论文阅读器 | 支持论文详情查看、PDF 阅读和围绕论文提问 | 本地 PDF 代理/落盘 + 全局会话共享 + paper_id 上下文注入 |
| 每日/周/月简报 | 自动把热点信息整理成结构化摘要 | LLM 生成简报 + 模板体系 + MySQL 缓存 |
| 用户系统 | 支持登录、权限控制、简报订阅 | 邮箱 OTP + JWT + RBAC |
| 运维监控 | 支持手动采集、调度查看、监控健康度 | FastAPI Ops API + Scheduler + Monitor API |

## 3. 核心功能有哪些，以及怎么实现

## 3.1 多源采集与内容入库

### 功能价值
把 AI 相关的论文、代码仓库、新闻、产品、社区热帖统一汇总，形成平台的数据底座。

### 实现思路
- 采集源包括 **HuggingFace Papers、GitHub Trending、Techmeme、Product Hunt、Hacker News**。
- 后端通过统一编排器把不同来源的抓取流程抽象成标准结果。
- 采集完成后不是直接存原始数据，而是会进一步做内容丰富与结构化处理。

### 关键实现点
1. **统一爬虫抽象**：不同来源的采集器都通过统一基类封装，降低新增数据源的成本。
2. **异步并发采集**：多个来源并行执行，避免整体吞吐受单一来源拖慢。
3. **内容丰富**：
   - ArXiv 先用摘要快速入库，再异步下载 PDF 并解析全文；
   - GitHub 抓 README；
   - 新闻/社区帖会进一步抓取详情正文。
4. **三库写入**：
   - MySQL 存结构化主数据；
   - Milvus 存向量索引；
   - Neo4j 存论文知识图谱。
5. **排行快照**：把每日排行写入快照表，给 Dashboard 和问答场景提供“按日回看”的能力。

### 面试可讲点
这部分体现的是 **数据工程能力**，不只是“爬下来”，而是做成了后续可问答、可分析、可展示的数据底座。

---

## 3.2 Dashboard 仪表盘

### 功能价值
让用户快速看到“今天 AI 圈发生了什么”，适合做首页冷启动和热点消费入口。

### 实现思路
- 提供热门文档排行、趋势雷达、统计卡片、来源分布、GitHub 热榜等内容。
- 仪表盘接口使用 Redis 做缓存，兼顾性能和成本。
- 对“当天榜单”做定榜/静默期控制，避免榜单频繁抖动影响用户感知。

### 关键实现点
1. **排行榜来自快照数据**，保证“今天榜单”可复现，不会因实时更新而不稳定。
2. **统计卡片是真实业务数据**，例如注册用户数、今日新增文档数、今日独立访客数。
3. **访客统计使用 Redis Set 去重**，实现简单但性能稳定。
4. **GitHub 热榜不是简单按 Star 排序**，而是结合增长、基线和年龄修正做热度计算，更贴近“热度”而不是“历史累计量”。

### 面试可讲点
这一块体现的是 **产品数据化展示能力 + 缓存与口径设计能力**。

---

## 3.3 RAG 智能问答

### 功能价值
用户不需要自己翻排行榜或逐条看资讯，可以直接提问，例如：
- 今天 GitHub Top10 有哪些？
- 最近值得关注的 AI 论文有哪些？
- 帮我总结一下多模态方向的热点。

### 实现思路
平台不是直接把大模型接到聊天框，而是做了 **RAG 检索增强生成**，让回答建立在平台自己的资讯数据之上。

### 关键实现点
1. **混合检索**：
   - Milvus 做向量检索；
   - Neo4j 做图谱检索；
   - MySQL 做兜底关键词检索；
   - 还会做 source fallback，保证不同来源都有覆盖。
2. **精排优化**：
   - 对召回结果做 rerank，提高相关性；
   - 当向量结果本身就不够相关时，自动跳过远程精排，减少延迟和 API 成本。
3. **Tool Use 能力**：
   - LLM 第一轮先判断要不要查库；
   - 如需查排行榜、知识库统计等结构化信息，就调用后端工具；
   - 第二轮再结合工具结果 + 检索结果生成最终回答。
4. **联网搜索增强**：
   - 支持平台内数据与外部 Web Search 并发补充；
   - 外部搜索失败不会阻断主流程。
5. **真流式 SSE**：
   - 后端边生成边推送；
   - 前端实时展示 `status / sources / thinking / content`；
   - 避免“全部生成完才一次性返回”的等待感。
6. **会话持久化**：
   - 问答结束后统一落盘用户消息与助手消息；
   - 支持历史会话、删除、重生成、LRU 清理。

### 面试可讲点
这部分最适合突出：
- 你不是只会“接个大模型 API”；
- 而是做了 **检索、结构化查询、流式输出、会话管理、性能优化** 的整套链路。

---

## 3.4 论文阅读与围绕论文提问

### 功能价值
对于 AI 垂类用户，论文阅读是高价值场景。用户可以先看论文信息和 PDF，再围绕这篇论文继续提问。

### 实现思路
- 平台提供论文搜索、论文详情、PDF 代理访问和论文阅读页。
- ArXiv 论文支持本地 PDF 下载与全文解析，方便后续做更高质量问答。
- 阅读页与聊天页共享全局会话，避免多套会话体系导致体验割裂。

### 关键实现点
1. **PDF 代理和本地化处理**：解决跨域访问问题，也为全文解析打基础。
2. **异步补全全文**：论文先快速可用，再后台下载 PDF、切片、向量化。
3. **paper_id 上下文注入**：用户提问时带上论文上下文，让回答更聚焦当前论文。
4. **会话共享方案**：论文阅读页最终改成与聊天页共用全局会话，减少状态复杂度。

### 面试可讲点
这里能体现你对 **用户体验与系统复杂度平衡** 的思考：不是功能越细越好，而是选择更稳定、认知负担更低的方案。

---

## 3.5 自动简报生成

### 功能价值
把原始资讯再向上加工一层，输出更适合“快速消费”和“订阅分发”的内容。

### 实现思路
- 支持日报、周报、月报；
- 支持综合、论文、GitHub、新闻、产品、社区等多个维度；
- 可流式生成，也可缓存历史结果。

### 关键实现点
1. **多模板体系**：针对不同源类型使用不同 Prompt 模板。
2. **缓存设计**：按日期、来源、周期做唯一缓存，避免重复生成。
3. **截断续写**：如果 LLM 输出被截断，会自动续写，保证结果完整。
4. **标签体系优化**：输出时强制带来源标签和领域标签，方便阅读、检索和后续二次利用。
5. **邮件订阅**：支持用户订阅和发送到邮箱，形成闭环。

### 面试可讲点
这体现的是项目不仅能“查”和“问”，还能主动“产出内容”和“分发内容”。

## 4. 系统整体架构与数据流

## 4.1 架构分层

项目整体可以概括为四层：

1. **前端展示层**：Vue 3 + TypeScript，承载 Dashboard、问答、简报、论文阅读、监控等页面；
2. **后端服务层**：FastAPI 统一提供 API、RAG 服务、采集编排、简报生成、认证鉴权、调度管理；
3. **存储检索层**：MySQL、Milvus、Neo4j、Redis、本地 PDF；
4. **外部数据与模型层**：五大资讯源 + 各类 LLM/Embedding/Reranker 服务。

## 4.2 核心链路说明

### 链路一：资讯采集链路
`外部数据源 -> 爬虫采集 -> 内容丰富 -> 评分/筛选 -> MySQL/Milvus/Neo4j -> Dashboard/RAG/简报消费`

这条链路的核心价值是把“外部离散网页”变成“内部统一知识资产”。

### 链路二：RAG 问答链路
`用户提问 -> 会话校验 -> 混合检索/工具调用/联网搜索 -> 精排 -> LLM 流式生成 -> SSE 返回前端 -> 会话落盘`

这条链路体现的是项目最核心的 AI 能力闭环。

### 链路三：简报生成链路
`快照/文档数据 -> Prompt 模板拼装 -> LLM 生成 -> MySQL 缓存 -> 页面查看/邮件发送`

这条链路体现的是“从数据资产到内容产品”的转化。

## 5. 技术亮点

## 5.1 技术亮点 / 难点 / 可优化点

### 技术亮点
1. **多源异构数据统一治理**：不同站点结构差异大，但最终统一成标准文档模型。
2. **三种存储协同**：MySQL 管结构化、Milvus 管语义检索、Neo4j 管关系知识。
3. **RAG 不止向量检索**：加入图检索、数据库兜底、Tool Use、Web Search，回答能力更稳。
4. **真流式问答体验**：后端按事件实时推送，前端可感知状态、来源、思考和正文。
5. **工程化较完整**：包含调度、监控、权限、缓存、订阅、评估、后台运维等，不是单点 Demo。
6. **围绕 AI 垂类做了场景化设计**：论文阅读、热点排行、简报订阅、GitHub 热榜都比较贴合目标用户。

### 项目难点可以怎么讲
1. **多源采集稳定性**
   - 难点：不同数据源页面结构、接口方式、频率限制都不同。
   - 应对：做统一爬虫抽象、异常隔离、并发调度、慢速 PDF 下载、单源独立采集。
2. **RAG 相关性与时效性的平衡**
   - 难点：纯向量检索不一定能回答“今天 top10”这类强结构化、强时效问题。
   - 应对：引入 Tool Use 和排行榜直查，把结构化数据注入上下文。
3. **回答质量和响应速度的平衡**
   - 难点：精排和联网搜索能提升质量，但会增加延迟。
   - 应对：并发执行、智能跳过 rerank、失败自动降级、流式输出掩盖等待时间。
4. **会话系统复杂度控制**
   - 难点：聊天页、论文页、多轮历史、重生成都涉及状态一致性。
   - 应对：统一会话模型、服务端持久化、前端按 conversation event 回填。

### 可优化点
1. **补全文档评估体系**：当前主观评估仍较弱，可进一步引入人工标注集和自动评测集。
2. **索引服务模块收敛**：当前部分切片/向量逻辑分散在仓储和下载器中，可进一步模块化。
3. **视觉问答持久化**：视觉流当前仍偏临时态，后续可并入统一会话体系。
4. **更细的缓存与热榜策略**：可引入分层缓存和更精细的热度衰减模型。
5. **多租户/权限扩展**：如果未来商用，可加组织空间、私有知识库、配额体系。

## 6. 面试答辩怎么讲更顺

## 6.1 电梯陈述（30~60 秒）

可以这样讲：

> 我做的是一个 AI 垂类资讯聚合和智能问答平台，核心目标是解决 AI 信息过载问题。系统会自动采集 HuggingFace Papers、GitHub Trending、Techmeme、Product Hunt、Hacker News 这几类来源的数据，做内容丰富、评分和多存储索引，然后提供 Dashboard 热点查看、RAG 智能问答、论文阅读和自动简报生成能力。技术上我重点做了多源采集编排、MySQL+Milvus+Neo4j 的混合检索架构、支持 Tool Use 的 RAG 问答链路，以及流式交互和会话持久化，让它不只是一个资讯站，而是一个可追问、可订阅、可持续演进的 AI 情报平台。

## 6.2 3 分钟模块化讲解提纲

### 第一段：先讲业务价值
- AI 信息太碎片化；
- 用户需要一个统一入口；
- 所以我做了聚合、问答、简报三个层次。

### 第二段：讲系统主链路
- 数据怎么采；
- 采完怎么入 MySQL / Milvus / Neo4j；
- 用户提问后怎么检索、精排、生成并流式返回。

### 第三段：讲两个技术亮点
建议优先讲：
1. **RAG + Tool Use**，为什么能回答榜单和统计类问题；
2. **采集到问答的完整闭环**，说明你做的是完整系统而不是单点功能。

### 第四段：讲难点和优化
- 多源异构数据稳定性；
- RAG 质量和时延平衡；
- 会话与状态一致性；
- 后续如何继续优化评估、视觉问答、模块收敛。

## 7. 面试答辩话术建议

### 如果面试官问“你的项目核心壁垒是什么？”
可以回答：

> 核心壁垒不只是采集，而是把采集、索引、问答、简报、订阅打通成了一个完整链路。尤其是 RAG 部分，我没有停留在简单向量检索，而是加入了数据库直查、图检索、精排和 Tool Use，所以它对时效性问题、排行榜问题、统计类问题的支持更好。

### 如果面试官问“你在里面最有技术含量的部分是什么？”
可以回答：

> 我会重点讲 RAG 问答链路和多源采集编排。前者涉及混合检索、流式输出、会话持久化和性能优化；后者涉及异构数据治理、异步任务编排和多存储协同。它们共同决定了这个系统能不能从资讯平台升级成智能情报平台。

### 如果面试官问“这个项目还有哪些不足？”
可以回答：

> 我觉得目前最大的不足主要有三个：第一，评估体系还可以更系统；第二，视觉问答还没有完全并入统一持久化会话；第三，一些索引能力还可以继续模块化收敛。这些问题并不影响主链路可用，但会影响后续可维护性和上限。

## 8. 一句话总结

如果用一句话总结这个项目，我会说：

> 这是一个把 **AI 热点采集、知识索引、RAG 问答、论文阅读和自动简报** 串成闭环的 AI 情报平台，重点价值在于把“分散资讯”转化成“可检索、可追问、可订阅”的高价值信息服务。
