# AIGCNEWS 项目全景概述

> 最后更新：2026-07-29  
> 文档定位：从产品、功能、架构、数据、部署和工程状态等角度总结项目当前全貌，不展开到具体代码文件与实现行。

## 一、项目概述

AIGCNEWS 是一套面向 AI 工程师、研究人员、产品经理和外部 AI Agent 的垂直情报平台。它持续采集 AI 领域的论文、开源项目、行业新闻、新产品和社区热点，将分散的公开信息加工成可浏览、可搜索、可收藏、可订阅，并可由 AI 客户端直接调用的数据资产。

项目目前形成了四条主要产品线：

1. AI 资讯与趋势看板；
2. AI 开源项目和工具目录；
3. 自动简报与邮件订阅；
4. 面向 Claude Code、Codex、VS Code 等客户端的 MCP 数据服务。

系统同时具备 RAG、论文阅读、附件、多模态和对话能力。不过，当前通用聊天和论文 AI 对话的 Web 入口处于维护状态，因此现阶段稳定开放的产品主体是 Dashboard、项目目录、论文发现与阅读、简报、MCP 和管理后台。

一句话概括：

> AIGCNEWS 是一个把 AI 领域公开信息加工为可浏览、可检索、可订阅、可收藏、可由 AI 客户端调用的垂直情报基础设施。

## 二、项目解决的问题

### 2.1 信息来源分散

AI 从业者通常需要分别浏览论文榜单、GitHub Trending、科技新闻、Product Hunt、Hacker News 和工具导航站。AIGCNEWS 将这些来源汇聚到统一入口，并提供一致的数据结构、历史快照、排行榜和检索能力。

### 2.2 原始信息缺少加工

系统并非只保存标题和链接，还会继续执行：

- 正文、README 或 PDF 补全；
- 内容评分、筛选和分类；
- 项目标签及中英文描述富化；
- 日、周、月榜单快照；
- GitHub 增长和热度计算；
- 向量索引和论文图谱构建；
- 智能简报生成；
- 历史数据归档。

因此，平台沉淀的是经过加工的结构化情报，而不是普通书签集合。

### 2.3 信息难以进入 AI 工作流

传统资讯网站主要面向人类浏览。AIGCNEWS 进一步通过 MCP 暴露论文、项目、榜单、分类和简报数据，使外部 AI 客户端能够直接调用这些能力。登录用户还可以签发最小权限 Token，让外部客户端只读访问自己的项目收藏。

## 三、目标用户

### 3.1 AI 工程师和开发者

这类用户可以寻找 Agent、RAG、MCP、LLM 等方向的开源项目，查看近期增长，按语言和分类筛选候选，并将项目保存到个人收藏。公共 GitHub 项目默认执行至少 500 Stars 的准入门槛，以减少未经验证的低质量候选。

### 3.2 AI 研究人员和论文读者

研究人员可以查看热门论文、搜索标题和摘要、阅读或下载 PDF，并将论文数据引入语义检索和 MCP 研究工作流。围绕论文的 AI 问答链路已经具备技术基础，但当前 Web 入口尚未稳定开放。

### 3.3 产品经理、创业者和行业观察者

Dashboard 和智能简报帮助用户快速了解当日热点、项目增长、新产品发布和社区话题，并通过日报、周报、月报和邮件订阅降低持续跟踪成本。

### 3.4 外部 AI Agent

Claude Code、Codex、Continue、VS Code 等宿主可以将 AIGCNEWS 作为专门的 AI 情报后端。由此，AI Agent 本身也是平台的一类用户。

### 3.5 平台管理员

管理员负责内容和系统运营，包括触发采集、按日期补采、刷新项目指标、生成简报、清理缓存、管理模型 Provider、管理外部 MCP Server，以及查看任务和服务健康状态。

## 四、核心产品能力

### 4.1 多来源自动采集

平台重点覆盖五类来源：

| 类型 | 主要来源 | 核心用途 |
|---|---|---|
| 论文 | HuggingFace Papers、ArXiv | 论文排行、详情、PDF、全文语义检索 |
| 开源项目 | GitHub Trending、GitHub API | 项目发现、指标、热度和语义搜索 |
| 行业新闻 | Techmeme | AI 与科技行业动态 |
| 新产品 | Product Hunt | 新发布产品和工具发现 |
| 社区热点 | Hacker News | 开发者社区讨论趋势 |

系统通过统一采集抽象对接不同来源。单个来源失败时尽量隔离错误，不阻断其他来源。采集结果会经过标准化、内容补全、评分、分类和多存储写入，最终服务于 Dashboard、项目搜索、RAG、简报和 MCP。

### 4.2 Dashboard 趋势看板

Dashboard 是主要公共入口，提供：

- 多来源统计；
- 日、周、月周期切换；
- Top 榜单；
- 历史日期回看；
- 可用快照日期；
- 今日新增、用户和访客统计；
- 采集中、静默期、已定稿和无数据状态。

榜单主要基于历史快照，而不是每次请求临时计算。这使某一天的榜单可以稳定复现，也避免采集过程中排名频繁抖动。

GitHub 热度不仅考虑累计 Stars，还综合增长速度、项目体量、维护活跃度、社区参与度、项目年龄和近期更新情况。

### 4.3 AI 项目目录

项目目录是当前产品完成度最高的模块之一，支持：

- GitHub AI 项目和工具网站；
- 全部、今日热门和站长推荐；
- 分类、子分类和编程语言筛选；
- 关键词与语义搜索；
- 相关性、热度、Stars、更新时间、收录时间和名称排序；
- 项目增长指标和可用状态；
- 中英文描述及标签；
- 分页、页码跳转和 URL 状态同步。

筛选条件会写入 URL，因此搜索结果可以刷新恢复、复制分享，并支持浏览器前进和后退。

项目搜索采用分层策略：先从 PostgreSQL 获取关键词候选，可选并行进行 Milvus 语义召回，再融合候选、回库水合完整数据、应用准入和分类过滤，并按指定策略排序。只有本地完全没有结果且满足严格条件时，才会调用有限的 GitHub Search fallback。

### 4.4 个人收藏与工具书架

登录用户可以收藏 GitHub 项目，并跨设备同步个人收藏和标签。前端使用乐观更新，在请求失败时自动回滚。

用户还可以建立私人工具网站书架：

- 提交 URL 并自动提取信息；
- 自动提取失败时手工填写；
- 编辑标题、中英文描述、分类、标签和图片；
- 删除私人网站。

个人网站不会自动混入公共项目目录，公共数据和私人数据保持清晰边界。

### 4.5 全局搜索与论文阅读

全局搜索目前主要用于论文和内容发现。空查询可以展示当日热门内容，输入后采用防抖搜索。论文结果可进入站内阅读页，其他结果跳转原始来源。

论文阅读能力包括：

- 论文详情；
- 浏览器内 PDF 渲染；
- 分页加载和进度显示；
- 原始 PDF 下载；
- 桌面双栏和移动端单栏布局；
- 页面区域框选与截图。

论文采集采用两阶段策略：先用摘要快速入库，让论文尽快可搜索；后台再下载 PDF、解析全文、切片并建立向量索引。

### 4.6 RAG 与聊天

后端已经具备较完整的混合 RAG 链路：

1. PostgreSQL 文档 ID 精确召回；
2. 标题和关键词匹配；
3. Milvus 向量召回；
4. Neo4j 图关系召回；
5. 来源补充、去重和均衡；
6. Reranker 精排；
7. 可选联网搜索；
8. LLM 流式生成。

聊天领域支持多会话、历史消息、重新生成、中止生成、图片和 PDF 附件、Thinking 与正文分阶段展示、来源引用、Markdown、数学公式、代码高亮和普通用户每日配额。

需要注意：底层能力完整度较高，但当前通用聊天和论文 AI 对话的前端入口处于维护状态。因此，它们应被描述为已经实现的技术能力，而不是当前稳定开放的核心功能。

### 4.7 多模态和附件

系统支持图片、PDF 和论文截图分析，包括 MIME 类型校验、大小限制、PDF 文本提取、附件解析状态和视觉模型流式输出。

视觉图片采用短期内存缓存，避免临时图片落盘。当前视觉消息尚未完全进入统一会话持久化模型，内存缓存也不适合多实例共享，因此这部分仍处于 Beta 阶段。

### 4.8 智能简报

简报支持综合、论文、GitHub、新闻、Product Hunt 和 Hacker News 等方向，并提供日报、周报和月报。

主要能力包括：

- 按日期读取历史简报；
- 优先使用缓存；
- SSE 流式生成；
- Markdown 和公式渲染；
- 中英文内容；
- 登录用户订阅和取消订阅；
- 多来源订阅；
- 立即发送到注册邮箱；
- 管理员批量生成。

部分来源只提供日度采集，因此其周报和月报能力受底层数据周期限制。

### 4.9 MCP 数据服务

MCP 是项目最有差异化的能力之一。

公共能力包括：

- 论文搜索和详情；
- 跨来源内容搜索；
- AI GitHub 项目搜索；
- 通用 GitHub 项目搜索；
- 项目分类；
- 日、周、月榜单；
- Dashboard 和简报资源；
- 项目发现与研究类 Prompt。

登录用户可以创建只读 MCP Token，让外部客户端访问自己的项目收藏。Token 明文只在创建时展示一次，服务端保存摘要，并支持设备标签、有效期、最后使用时间、作用域和撤销。

前端 MCP 页面提供 endpoint 握手、工具发现、多客户端和多 Shell 配置、命令生成、Token 管理以及安全提示，已经形成相对完整的开发者接入体验。

## 五、整体技术架构

### 5.1 前端

前端以 Vue 3、TypeScript、Vite、Vue Router、Pinia、Tailwind CSS 和 Vue I18n 为核心，配合 Markdown、HTML 清洗、数学公式、代码高亮和 PDF 渲染能力。

架构正从大型页面组件逐步演进为：

- 页面负责布局与依赖装配；
- 业务组件负责局部交互；
- Composable 负责页面状态和异步编排；
- Feature Model 负责纯业务逻辑；
- Service 负责 HTTP 访问；
- Pinia 保存真正需要跨页面共享的状态。

全局状态主要集中在认证和聊天领域，Dashboard、项目目录、简报和 MCP 更多采用页面级状态。

### 5.2 后端

后端是 FastAPI 单体应用，但内部已经形成较清晰的分层：

1. Transport/API 层：REST、SSE、MCP、鉴权和 DTO；
2. Application/Service 层：采集、RAG、项目发现、简报、会话和 MCP 应用服务；
3. Repository Protocol 层：按用户、文档、会话、项目、简报等能力拆分数据端口；
4. Infrastructure Adapter 层：PostgreSQL、Milvus、Neo4j、Redis、SMTP、GitHub、网页抓取和模型服务。

FastAPI 生命周期是统一组合根，负责建立 PostgreSQL 连接池、组装 Repository、初始化 Redis、启动调度器、预热语义检索和精排能力，并在关闭时释放资源。

### 5.3 存储职责

| 存储 | 主要职责 |
|---|---|
| PostgreSQL 16 | 结构化事实、用户、会话、项目、简报、任务和配置主库 |
| Milvus | 文档、论文正文和项目的语义向量索引 |
| Neo4j | 论文实体与关系图谱 |
| Redis | API 缓存、邮箱验证码、防刷和访客去重 |
| MinIO、etcd | Milvus 的对象存储和元数据依赖 |
| 本地文件 | 论文 PDF、部分附件和模型缓存 |

PostgreSQL 是结构化主数据来源；Milvus、Neo4j 和缓存属于可重建的派生能力。跨存储采用最终一致性，而不是分布式事务。

## 六、核心数据流

### 6.1 采集链路

```text
外部数据源
→ 抓取与标准化
→ 正文、README 或 PDF 补全
→ 分类、评分与富化
→ PostgreSQL 主写
→ 排行快照
→ Milvus 向量索引
→ Neo4j 图谱补写
→ 缓存失效
→ Dashboard、搜索、RAG、简报和 MCP 消费
```

处理原则包括：

- 单个来源失败不阻断其他来源；
- 部分 enrichment 失败不回滚已成功的主数据；
- 写入尽量幂等；
- 派生索引通过重试、重新索引和 backfill 修复。

### 6.2 项目搜索链路

```text
用户查询
→ 查询意图和技术词解析
→ PostgreSQL 关键词候选
→ Milvus 语义候选
→ 候选融合
→ PostgreSQL 完整数据水合
→ Stars、分类、语言和范围过滤
→ 相关性或热度排序
→ 可选 rerank
→ 本地零结果时有限 GitHub fallback
```

### 6.3 Chat SSE 链路

```text
用户提问
→ 权限和配额检查
→ 混合检索
→ 去重与精排
→ 输出来源
→ 流式输出 Thinking
→ 流式输出正文
→ 完成后事务性保存消息
→ 返回会话和消息标识
→ DONE
```

如果流开始后发生错误，HTTP 状态通常已经无法更改，只能通过 SSE 错误事件通知客户端。消息一般在完整生成后持久化，因此数据库不会保存逐 Token 的中间态。

### 6.4 简报链路

```text
历史快照和文档
→ 按来源、周期和语言组织上下文
→ LLM 流式生成
→ PostgreSQL 缓存
→ Web 阅读
→ 邮件订阅分发
```

## 七、定时任务与后台执行

调度器运行在 FastAPI 进程内，使用中国时区，主要任务包括：

- 五类来源错峰采集；
- GitHub 每日项目流水线；
- GitHub 指标定期刷新；
- 每日简报生成；
- 项目语义搜索预热；
- 会话数据定期清理；
- 启动后补齐近期论文快照和当日 GitHub 指标。

当前部署是单后端实例，因此进程内调度和互斥可以正常工作。如果未来横向扩容，需要保证只有一个实例运行调度器，或引入跨实例分布式锁及独立 Worker。

部分 PDF 补全仍依赖后台线程，不具备持久消息队列的可靠性。进程重启后，未完成任务需要通过后续扫描和 backfill 恢复。

## 八、外部协议兼容边界

项目将 REST、MCP 和 SSE 视为稳定契约，内部重构不能随意改变外部行为。

### 8.1 REST

需要保持路由、字段、分页、排序、错误状态、权限、项目 Stars 门槛和 fallback 来源信息。

### 8.2 MCP

需要保持 JSON-RPC envelope、初始化行为、工具和资源定义、文本结果、结构化结果、工具级错误、兼容别名、Token scope 和私人数据隔离。

### 8.3 SSE

需要保持事件名称、数据分隔、sources、thinking、content、conversation、error、heartbeat、`[DONE]` 和断开后的持久化语义。代理层必须关闭不适合流式响应的缓冲和缓存。

## 九、PostgreSQL-only 数据库现状

### 9.1 已完成的切换

PostgreSQL 16 已经成为唯一在线关系型数据库，具体表现为：

- 主部署栈不再包含 MySQL；
- 应用启动只组装 PostgreSQL Repository；
- 业务通过 Repository Protocol 使用数据能力；
- 就绪检查明确以 PostgreSQL 为关系型运行时；
- 数据库后端选择分支已删除；
- 项目目录数据库影子模式已删除；
- REST、MCP、调度、采集和项目目录都已切换到 PostgreSQL 主路径。

### 9.2 迁移和验证证据

当前已有证据支持：

- 应用数据已经迁移；
- 两轮最终核对结果匹配；
- 表行数、主键或业务键摘要和整行摘要匹配；
- Sequence 高水位完成核对；
- 关键外键没有发现孤儿；
- MySQL 最终备份和 PostgreSQL 最终备份均已生成并附带校验和；
- PostgreSQL 备份已经在隔离空库恢复并通过验证。

因此，数据库切换已经是主干上的当前事实，而不是试运行状态。

### 9.3 尚未完全结束的工作

MySQL 当前是“运行时退役”，不是“代码完全清零”。代码库仍保留一部分迁移适配器、核对服务、隔离恢复工具、历史测试和旧术语。

后续应在灾难恢复观察期结束后：

- 删除在线代码中的 MySQL Repository；
- 将必要恢复工具隔离为独立 operator；
- 从生产依赖中移除无用驱动；
- 清理误导性配置和命名；
- 保留最小化、受控的离线恢复能力。

旧 MySQL 卷仍属于灾难恢复材料，没有针对精确卷名的独立授权时不得删除。

### 9.4 当前回滚原则

当前不再允许通过配置直接切回 MySQL。故障处理应优先：

1. 停止或限制新写入；
2. 保全 PostgreSQL 和迁移证据；
3. 优先恢复 PostgreSQL；
4. 必要时回滚应用版本；
5. 只有 PostgreSQL 灾难恢复不可行且获得额外授权时，才在隔离环境恢复 MySQL。

如果 PostgreSQL 已经产生新写入，直接切回冻结时的 MySQL 会造成数据分叉和丢失。

## 十、前端体验与设计状态

前端主要采用顶部全局搜索、中部工作区和底部 Dock 导航。Dashboard 和项目目录使用页面缓存，切换页面后尽量保留筛选和已加载数据。

移动端针对底部安全区、动态视口、横向滚动导航和单栏布局做了适配，并考虑 reduced-motion。

当前视觉方向偏向：

- 暖白纸张背景；
- 深色硬边框；
- 荧光黄绿色强调；
- 硬阴影；
- 编辑部和纸面终端式风格。

### 11.1 测试体系

项目拥有较丰富的前后端测试，主要覆盖：

- Repository 契约；
- PostgreSQL 查询和事务；
- 数据迁移、核对和恢复；
- REST、MCP 和 SSE；

CI 会执行后端测试、PostgreSQL 16 集成测试、数据库迁移、前端单元测试、TypeScript 类型检查和前端生产构建。

### 11.2 当前质量短板

## 十二、部署与运维

### 12.1 主部署形态

当前采用单机 Docker Compose，主要服务包括：

- Nginx 前端；
- FastAPI 后端；
- PostgreSQL；
- Redis；
- Milvus；
- etcd；
- MinIO；
- Attu；
- Neo4j；
- 并行托管的 PriceAI 服务。

系统不是 Kubernetes 架构，也没有多节点、自动水平扩容或零停机滚动发布。

### 12.2 网络入口

主站链路大致为：

```text
客户端
→ Nginx
→ 静态前端
→ /api
→ FastAPI
```

Nginx 负责 TLS、HTTP 跳转 HTTPS、SPA 路由回退、静态资源缓存、API 反向代理和 SSE 代理兼容。

核心栈（后端 API、前端、PostgreSQL、Redis、Milvus、MinIO、Neo4j）单凭当前仓库即可完整复现（见 README 快速开始）。参考生产部署还涉及远程 Caddy VPS、WireGuard、Cloudflare Tunnel、私网代理、外部部署控制器，以及姊妹服务与私有 nginx server 等边缘配置——这些以私有 overlay 形式位于仓库之外（`docker/docker-compose.yml` 头部注释描述了注入机制），属可选的私有部署扩展，不影响核心栈独立运行。

### 12.3 开机恢复

系统通过 Docker restart policy 和 systemd oneshot 两层机制恢复服务，并固定 Compose project name、校验配置、等待健康检查和清理孤立容器。

该方案适合受控单机或小规模生产，但不属于零停机、多副本的云原生发布体系。

## 十四、主要风险与技术债

### 14.1 迁移制品治理

数据库 dump、恢复证据和核对报告不应长期放在源码工作区。这些材料可能包含用户和业务数据，应移入加密、受控的备份存储，Git 中只保留脱敏结论和必要校验摘要。

### 14.2 基础设施暴露面

内部的 Redis、Milvus、MinIO、Attu、Neo4j 和后端管理面应尽量只在 Compose 网络、loopback、VPN 或管理网可见，公网入口应收敛到 Nginx。

### 14.3 默认凭据和密钥管理

仍需要进一步替换开发型默认凭据，引入生产配置门禁、密钥轮换和更正式的 Secret 管理，并避免证书私钥进入镜像层。

### 14.4 可观测性不足

当前已有健康检查、任务状态和少量指标，但缺少完整的标准指标、集中日志、调用链追踪、自动告警、数据库连接池指标、SSE 指标、LLM 成本和数据新鲜度监控。

### 14.5 全栈灾备不完整

PostgreSQL 逻辑备份和恢复已验证，但仍缺少 WAL/PITR、自动异地备份、统一 RPO/RTO，以及 Milvus、MinIO、etcd、Neo4j、Redis 和 PDF 的同等级恢复方案。

### 14.6 多存储最终一致性

跨 PostgreSQL、Milvus、Neo4j、Redis 和文件系统写入时，可能出现主数据成功而派生索引失败。后续需要强化持久任务、幂等重放、索引状态、重建工具和定期一致性巡检。

### 14.7 MySQL 遗留代码

MySQL 在线实现已清理完毕：`mysql_repo.py`、迁移期 transfer/reconciliation 核心与 MySQL 基建已删除（62adb9f），config 中的 MySQL/SQLite 死字段已清理（6af16b8）。仅剩少量历史命名残留（如 `retriever.py` 中沿用 MySQL/SQLite 字样的方法名），不影响行为，清理进行中。

### 14.8 调度器单实例假设

当前调度器依赖单后端实例。如果未来横向扩容，需要拆分独立 Worker，或增加跨实例互斥机制。

### 14.9 RAG 开放状态与实现状态不一致

底层 RAG 和聊天能力较完整，但 Web 入口关闭。项目需要明确下一步是重新开放对话产品，还是把产品重心继续放在项目发现、简报和 MCP。

## 十七、总结

AIGCNEWS 当前是一套以 PostgreSQL 为结构化主库，以 Milvus 和 Neo4j 提供语义与图检索，以 Redis 提供缓存和短期状态，以 Vue 3 提供 Web 体验，并通过 REST、SSE 和 MCP 对外服务的 AI 垂直情报平台。

它最强的地方不是某一个页面，而是已经形成完整闭环：

```text
多源采集
→ 内容加工
→ 结构化存储
→ 趋势排行
→ 项目发现
→ 语义检索
→ 智能简报
→ 用户收藏
→ Web 展示
→ MCP 开放
→ 管理运维
```

PostgreSQL-only 架构切换已经基本完成。当前项目的主要矛盾已经从“能否完成迁移”转变为“如何收口迁移遗留、提升安全和可观测性、完善全栈灾备，并把已有能力稳定地产品化”。

下一阶段最合理的策略不是继续高速扩充功能，而是进入一个明确的稳定化周期：先完成迁移治理、测试门禁、基础设施安全和运维能力，再决定重点扩大项目发现与 MCP，还是重新开放并强化 RAG 产品线。
