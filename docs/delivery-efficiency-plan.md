# 交付链路效率与无人值守改进方案

- 审查日期：2026-09-19；时间采用 UTC。
- 状态：审查记录与待实施方案。本次只新增文档，不表示下述能力已经实现，也不授权批量修改或部署控制器。
- 范围：提交、入队、CI、合并、制品、迁移、源站、公网发布、失败反馈和控制器恢复。
- 现行流程见 [本地交付控制器](local-delivery.md)，提交约束见 [Git 工作流](git-workflow.md)。本方案不覆盖现行门禁。

## 1. 目标与已确认的发布语义

目标是在保持必要验证、生产隔离和可追溯证据的前提下，减少重复工作，降低从提交到完整发布的耗时，让正常交付和常见基础设施故障无需人工操作。

用户已确认的累积发布流程：

> A 开始发布 → B、C 合入主线并排队 → A 完成发布 → 下一轮发布包含 A+B+C 的最新已验证主线。

规则：

1. 空闲时立即承接已有的合格候选，不额外等待凑批。
2. 当前候选一旦开始执行，就固定其源码和制品身份；不能仅因主线前进取消它。真实验证失败仍须停止。
3. 发布期间新合入的改动属于下一轮；下一轮取最新已验证主线，合并承接中间版本。
4. 已上线交付不会因后续候选失败变回等待；当前生产是否仍包含它需要独立验证。
5. 队列等待、资源等待、执行、失败、恢复中必须分别展示。

“无需人工操作”不等于“所有失败都强行继续”。无法证明安全时应保留当前生产版本、记录阻塞并通知；不承诺代码零缺陷。凭据失效、长期外部故障、有业务歧义的冲突和破坏性数据操作可能仍需要人工决定。

## 4. 分阶段发现与改进方向

### 4.1 提交与入队

已有自动 push、branch+SHA 去重、接收 hook 入队、分支扫描补偿、禁止强推和创建时任务归属。这些能力保留。

自动 push 失败只报告错误，提交仍然存在；Stop hook 可以拒绝虚假交接，但后台不会收编仅在工作区的未推送提交。可增加精确提交的待推送回执和有限补偿，不能后台提交未完成修改。

同一分支未执行的旧提交应由新提交替代。已经执行的旧检查只能在确认无用并能安全清理时取消，不得把取消当成功。

### 4.2 CI 调度与资源

当前调度器不断领取任务，每个任务申请五类检查，实际容器启动受共享池约束。多个任务可能显示 testing，但其检查仍在等待准入。

每个检查取得准入锁后重新建立观察策略；默认稳定观察 60 秒，观察和启动处于串行准入过程内。建议使用持续维护资源证据的统一调度器，保留压力、OOM、成员隔离和总预算验证，避免每个检查重复冷启动观察。不能直接删除等待窗口。

CI、生产制品构建和生产服务应纳入协调的资源规划；审查到的发布构建路径没有复用 CI 准入调度。实际宿主资源归属与容量仍需专项测量，不宣称已有统一资源预算。

### 4.3 集成与主线落地

当前各任务先完整验证自己的提交，落地前主线变化就 needs_update。应改为轻量预检并行、一个固定最终集成批次验证；批次空闲即取任务，有上限，不等待凑大批。

无冲突的机械整合在隔离工作区自动完成；真实冲突返回归属任务。验证期间新任务排下一批，不重建当前批次。最终落地必须与被验证提交一致，保留唯一主线写入者和 CAS。

代码审查发现：Git 主线更新、任务 landed、validated_main 更新分步完成。进程若在中间退出，可能造成主线已前进而验证元数据滞后。尚未进行故障复现。应增加落地意图和恢复核对，依据精确 CI 回执补齐记账，不绕过一致性门禁。

批次失败需要自动定位或拆分，并限制拆分验证成本；正常任务继续前进，失败任务不无限拖住队列。批次上限、公平性和超时应通过压测确定。

### 4.4 检查缓存和依赖下载

已安装执行器支持部分下载故障最多三次尝试，以及有环境指纹约束的检查或步骤复用；缓存默认一小时有效。测试失败、校验和错误不应通过重试刷绿。

当前验证指纹包含完整源码树，无关改动也可能使所有检查失效。组件级复用必须覆盖源码、测试、共享契约、依赖锁、配置、工具链与真实输入；不能只按目录猜测不受影响。先保留完整基线，证明依赖边界后再缩小复用范围。

预热工具链、固定依赖缓存和不可变模板可以减少下载和启动；可写缓存不能成为候选跨任务污染验证结果的渠道。

### 4.5 制品构建与身份

当前 CI 使用合成 UI 素材夹具，生产构建才加入真实目录、预览和私有制品。因此现有 CI 镜像不能直接提升为生产镜像。

目标是隔离源码验证后，由可信构建阶段加入经摘要验证的素材，构建一次生产制品并验证该制品，发布仅使用同一 digest。

三个服务目前顺序构建，全部完成才保存整套镜像检查点。建议增加逐服务输入摘要和完成回执，允许安全复用未变化服务；是否并行由资源测量决定。Docker 层缓存不等于完整的阶段恢复。

制品身份应覆盖源码树、依赖、Dockerfile、基础镜像、构建参数、工具版本、门禁版本和所有私有素材摘要；单个 Git SHA 不足以描述全部生产输入。

### 4.6 固定发布候选、超时与重启

当前部署前会重新检查候选是否仍是最新主线，较旧祖先返回 superseded，上层可能记成发布失败。这与已确认的固定候选语义不一致，须优先修正。

单条构建命令可等待 3600 秒，外层发布可等待 7200 秒。应区分网络连接超时、步骤时限和无进展检测，避免下载故障长期占用发布器。无日志不能单独作为杀进程依据。

超时、退出或重启后应核对锁、子进程、Docker 构建和实际生产版本，再决定清理或续跑。不能只修改任务状态而留下仍在运行的外部操作。

### 4.7 源站与公网恢复

底层在源站已为目标 SHA 时可以只做公网发布，但外层通常阻止同一失败 SHA 再次尝试，尚缺通用阶段续跑调度。

两个站点顺序发布，后一个失败可能留下源站与部分站点版本不一致。包装器记录 published，但重试时没有直接据此跳过成功站点。应保存并核对每站 release ID、摘要和实际版本，仅恢复未完成阶段；制定部分成功的期限与补偿策略，不宣称跨站原子切换。

保留静态发布已有的摘要校验、原子软链接切换、单站回滚和远端旧文件复用。公网 SSH、rsync 等也需要明确操作时限，不能完全依赖外层总超时。

### 4.8 数据库和业务验收

迁移已有 advisory lock、单迁移事务、执行账本和 checksum 漂移检查。多项迁移不是一个整体事务，前项成功后后项失败，前项变化仍保留。应用镜像回滚不会自动还原数据库。

采用兼容的新增结构、切换应用、后续删除流程；安全、权限、迁移和共享协议等高风险改动增加独立验证，必要时单独成批。

源站已有 Compose 健康等待及 live/ready 探针；公网检查首页、路由、静态资源等。审查时公网探针固定地址解析，不能单独证明公共 DNS/CDN 路径。应增加精确版本验证、少量关键业务契约和独立公共路径探针，不只检查 HTTP 200。

### 4.9 失败通知与自动修复闭环

已有精确归属、空闲/工作区检查、通知去重和成功不唤醒。发送超时保留 unconfirmed 是合理的防重复措施，但当前发送路径缺少自动核对回执、确认未送达后补偿的闭环。

accepted 不等于修复完成，执行过命令也不等于新提交通过验证。需要追踪故障身份、接收回执、修复提交、重新验证和最终故障解除。

Agent 忙、脏工作区、会话终止和归属不可用应分别处理；受控接管必须保留归属证据，不能按标题猜测或覆盖工作区。发布失败时“仅使用原分支”和“必须新建 session 修复已落地代码”的提示冲突需要消除。

### 4.10 控制器恢复、升级与状态一致性

systemd 会自动重启进程，但 CI 重启会把 claimed/testing 标为失败，执行器主要清理旧容器而不自动重跑，发布重启也会将 deploying 标为失败。这是安全停止，不是交付自动恢复。

需要依据持久阶段回执恢复，成功事实从真实外部状态重建。Git、SQLite、源站和公网不能组成一个事务，应通过幂等操作、执行归属与事后核对达到一致。

控制器应版本化安装、记录加载版本、排空后切换、自检和回退。可信门禁基线需单独受控升级，不能由候选自行改变，也不能把 main 合并误认为已安装生效。

看板和 Stop hook 应统一使用交付自身的完成证据及当前生产包含关系，不能让后续候选失败抹掉历史成功。构建、生产切换和完整公网交付应使用不同状态。

## 5. 推荐目标流程及方案取舍

推荐流程：任务快速预检 → 有上限的固定集成批次 → 精确候选验证与落地 → 可信生产制品构建/验证 → 固定候选源站发布 → 分站公网发布 → 完整交付回执。

最终制品构建是在落地前还是落地后完成，需在实施设计中明确；无论选择哪种，实际发布制品必须经过验证。源码验证与发布可以流水执行，但不能无预算争抢生产资源。

| 方案 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 每任务完整 CI，主线前进就重跑 | 简单保守 | 多任务下作废严重 | 不扩大 |
| 提前验证多个累积组合 | 可能降低个别任务延迟 | 前序失败导致重建，资源需求高 | 暂不采用 |
| 全部攒为大批次 | 检查次数少 | 等待长、失败定位难 | 不采用 |
| 空闲立即取有上限的小批次 | 限制作废、集中最终验证 | 批内失败需拆分 | 推荐验证 |

## 6. 实施顺序

| 阶段 | 工作单元 | 完成标准 |
| --- | --- | --- |
| 1：可靠恢复 | 固定发布候选；落地记账恢复；阶段回执；公网续跑；唤醒核对 | 常见中断可恢复，不重复危险操作，不误报成功 |
| 2：减少作废 | 小批次最终集成；旧任务去重；持续资源调度；分类有限重试 | 主线前进不再使整个并发队列反复验证 |
| 3：减少重复构建 | 可信制品构建一次；逐服务检查点；依赖和素材缓存 | 发布复用经验证制品，输入变化正确失效 |
| 4：精细优化 | 组件级检查复用；调度和资源参数优化 | 与完整验证对照证明不漏检，达到测量目标 |

每阶段拆成可审查、可回退的工作单元；不在一次变更中同时切换所有调度、缓存和恢复语义。保留现有精确 SHA、主线 CAS、隔离、迁移与健康门禁。生产验收按项目 verify 技能和相应高风险规则执行。

## 7. 效率预估：规划区间，不是承诺

| 场景 | 预估 | 限制 |
| --- | --- | --- |
| 单任务、无故障和主线竞争 | 完整交付时间减少约 20%～40% | 依赖缓存、构建占比及资源条件 |
| 多任务集中交付 | 整批完成时间减少约 40%～65% | 基于当前重复验证较多，须压测确认 |
| CI 参考目标 | 17 分钟样本尝试降至 10～14 分钟 | 仅 CI，不含发布；后端步骤约 12 分钟，本身也需优化才可能达到下沿 |
| 网络或执行中断恢复 | 预计显著减少等待和重复执行 | 缺少完整恢复时间基线，不报百分比 |
| 人工干预 | 正常流程零操作，覆盖的常见故障自动恢复 | 不承诺永久无人处理所有异常 |

各项收益不能相加。任务经过时间、整批完成时间、吞吐量和计算资源消耗是不同指标。小批次可能提高整体吞吐，但刚错过当前批次的单个任务仍需等待。

第一阶段总体规划目标：交付时间减少约三分之一，并显著减少人工救火；不是指仅做阶段 1 就必然获得该收益。不为了数字取消必要门禁，也不把少量样本外推为长期保证。

## 8. 测量与验收

实施前后记录精确任务、批次、候选、制品和控制器版本，分别测量排队、准入、准备、测试、构建、源站、公网、恢复时间；区分实际执行与复用。

按单任务、多个独立任务、热点冲突任务、冷缓存、热缓存及故障恢复分别比较，统计 P50/P95、整批耗时、作废验证比例、缓存命中率、失败重试率、CPU/内存开销和人工干预次数。样本量与任务组合须公开，不用单次最佳成绩宣称收益。

必需验收场景：

| 场景 | 预期 |
| --- | --- |
| A 发布时 B、C 合入 | A 不被取消；下一轮包含 A+B+C |
| 集成验证期间新任务到达 | 当前候选不变，新任务进入下一批 |
| 批内代码失败或真实冲突 | 不刷绿，定位/隔离后正常任务可继续 |
| Git 落地后元数据未写完就退出 | 重启核对精确回执并完成记账，无虚假成功 |
| 同一提交重复入队或同一分支更新 | 去重并淘汰未执行旧任务，不重放已完成交付 |
| CI/构建中断或下载超时 | 归属核对、有限恢复、清理有证据，无遗留执行者 |
| 源站成功、公网失败 | 恢复公网阶段，不重复成功的源站切换 |
| 第二个站点失败 | 明确部分成功，按策略恢复并重新验证各站版本 |
| 迁移失败或应用回滚失败 | 不伪称恢复成功，保留事实并阻断不安全继续 |
| 唤醒发送超时、Agent 忙或会话结束 | 核对回执和归属，不重复唤醒、不无限沉默 |
| 公共 DNS/CDN 与目标节点结果不同 | 分别报告，不能用固定地址探针代替公共路径验收 |
| 后续候选失败 | 仍被生产包含的已交付任务保持成功 |
| 控制器升级或回退 | 可确认实际加载版本，任务不中途丢失，旧记录可读取 |

自动恢复必须在隔离故障演练和必要的受控运行验收后才标为完成。单元测试通过、服务 active、通知 accepted 或一次正常发布成功，都不足以单独证明无人值守闭环成立。
