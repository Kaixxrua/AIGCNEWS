# 05｜系统架构设计师论文学习手册

> 用时：第 34～39 周，每周约 6～8 小时。
>
> 目标：在 120 分钟内写出扣题、可信、结构完整的架构论文，不把文章写成代码说明书。
>
> 说明：字数、评分和考试要求以当年度官方规则为准；本文的 2200～2500 字是训练目标。

## 1. 论文的核心任务

论文不是介绍“我用了哪些技术”，而是证明你能在真实约束下做架构决策。文章应形成一条证据链：

```text
背景与目标 → 约束和质量属性 → 总体架构 → 关键决策与取舍
           → 实施/治理 → 问题与改进 → 结果与总结
```

不要求实现新功能。你的优势是已经接触过一个真实产品，可以用架构图、故障经历、边界和决策写出可信叙事；但必须区分已证实事实、练习假设和未来建议。

## 2. AIGCNEWS 素材边界

可直接依据 [当前架构事实](../architecture.md) 和 [项目概览](../project-overview.md) 表达：

- 多源采集、标准化、富化和多种消费面；
- PostgreSQL 是结构化事实主库；
- Redis、Milvus、Neo4j 是可重建的派生能力；
- 跨存储采用最终一致，没有分布式事务；
- REST、SSE、MCP 有不同协议边界，MCP 入站由独立 Go 服务承载；
- nginx 提供公网边界，Docker Compose 负责当前部署形态；
- APScheduler 为进程内调度，横向扩容需治理单活；
- JWT、Token scope、限流、TLS、SSRF 防护和审计属于安全边界。

不能直接写成事实的内容：

- 用户数、日活、QPS、SLA、成本、团队人数；
- “性能提升 50%”“可用性达到 99.99%”等无来源数字；
- 尚未落地的分布式锁、消息队列、多活、读写分离或云迁移；
- 自己没有参与或无法核验的具体事故和结果。

需要数字时，写成“本文练习假设：……”，并在结尾说明这些数字用于设计推演，不是项目现状。

## 3. 推荐文章结构

### 3.1 开头：背景、目标和约束（约 300～400 字）

回答：项目服务什么业务、为什么需要建设、核心用户和功能是什么、规模/合规/交付有什么约束。不要用产品宣传语，要尽快引出架构问题。

**句式**：

> 本项目面向……，主要解决……。建设时重点约束包括……；其中……是最需要通过架构解决的质量属性。因此我采用……的总体思路。

### 3.2 总体架构（约 400～500 字）

先放一张简洁图，再用自然语言说明从输入到输出的路径。图中控制在 8～12 个关键节点，标出同步/异步、主库/派生、内外边界。

AIGCNEWS 图示可以是：

```text
数据源 → 采集与标准化 → 富化 → PostgreSQL 事实主库
        ├→ Redis 缓存/限流
        ├→ Milvus 向量索引
        └→ Neo4j 论文关系
客户端 → nginx/TLS → REST / SSE / MCP → Dashboard/搜索/推送/RAG
```

不要在图中塞入函数名、类名或源码细节。

### 3.3 关键决策一：事实主库与派生能力（约 500～600 字）

说明为什么 PostgreSQL 作为结构化事实来源，为什么索引/缓存可以异步建立，为什么接受短暂不一致，以及如何重试、补采、幂等和告警。对比“所有存储使用分布式事务”的替代方案，写清协调成本和可用性代价。

### 3.4 关键决策二：边界、扩展或安全（约 500～600 字）

根据题目选择一个主线：

- nginx 统一 TLS、路由、限流，SSE 关闭缓冲；
- MCP 因协议和运行边界独立承载，但其他模块不盲目微服务化；
- 调度单活与横向 API 扩展的冲突及治理；
- Token scope、最小权限、外部 URL SSRF 防护和审计。

一定要写替代方案、代价、失败模式和验证方法。

### 3.5 问题、改进和总结（约 300～400 字）

写一个真实可解释的问题：索引滞后、外部源失败、缓存故障、重复任务、代理缓冲或权限边界。说明发现信号、止损措施、根因、改进和如何验证。最后回扣题目主题，而不是只写“项目取得成功”。

## 4. 六周写作计划

| 周次 | 任务 | 自测时机 | 通过标准 |
|---:|---|---|---|
| 34 | 选 3 个题目，拆题和定立意 | 每题 20 分钟 | 每题写出主题、两决策、三属性 |
| 35 | 建立项目背景、约束、架构图 | 周末写 500 字 | 图和文字一致，事实有来源 |
| 36 | 写两个关键决策段落 | 周末写 1000～1200 字 | 每段含替代方案和代价 |
| 37 | 写问题、改进、验证段落 | 周末完成半篇 | 有故障闭环，不虚构指标 |
| 38 | 第一次整篇限时 | 120 分钟 | 2200～2500 字，结构完整 |
| 39 | 第二、三次整篇限时与修订 | 每周至少一次 | 连续两次达到自评及格线 |

论文训练期间每周至少保留一道下午案例题；论文不能替代案例能力。

```text

当前事实及文档来源：

关键决策二及替代方案：

```

## 6. 自测题和参考检查

### 自测一：立意（第 34 周）

题目主题为“论分布式系统中的数据一致性设计”。用 20 分钟完成：项目选择、背景三句、两个一致性决策、一个失败场景。

**通过线**：没有把“用了数据库”当作立意；至少写出事实主库/派生索引、强一致/最终一致的边界和一个补偿机制。

### 自测二：架构段（第 35～36 周）

只看题目和素材卡，画一张图并写 1000 字，要求解释两个决策。

**参考检查**：图中有内外边界、主库/派生、同步/异步箭头；每个决策均回答“为什么选、备选是什么、代价是什么、怎么验证”。

### 自测三：问题与改进（第 37 周）

写 400 字“派生索引滞后”段落。

**参考结构**：发现索引滞后 → 保留主库读取/提示结果不完整 → 检查任务失败与积压 → 重试和幂等 → 补建与告警 → 用滞后时间和成功率验证。不要声称具体指标已达成。

### 自测四：整篇限时（第 38～39 周）

从真题或模拟题中抽题，120 分钟完成约 2200～2500 字，最后 10 分钟专门查扣题、段落、事实和字数。

**自评 rubric（100 分）**：扣题 20；背景/约束 15；架构图与总体设计 15；两个关键决策及权衡 20；质量属性 10；问题与改进 10；结构/表达/时间 10。训练通过线 ≥60，且“扣题、决策权衡、问题改进”三项不能低于一半。

## 7. 常见失分与修复

| 问题 | 表现 | 修复 |
|---|---|---|
| 写成技术清单 | 一段堆很多组件，没有因果 | 每个组件后补“解决什么问题” |
| 写成项目宣传 | 全是“高效、稳定、领先” | 改成约束、方案、证据和代价 |
| 没有权衡 | 只说选择 A，不说为什么 | 加一个备选和一项代价 |
| 没有故障闭环 | 假设所有依赖永远正常 | 加发现、降级、恢复、验证 |
| 虚构指标 | 无来源的 QPS、SLA、百分比 | 删除，或显式标为练习假设 |
| 论文依赖代码 | 函数名、类名占据正文 | 换成边界、数据流和职责 |
| 偏离题目 | 背景很长，后文没回应题干 | 每个大标题旁写题目关键词 |

## 8. 阶段验收

第 39 周结束前：

- 完成至少 3 次限时写作，其中连续两次在 120 分钟内完成；
- 训练字数达到 2200～2500 字，文章有完整开头、架构图/总体设计、两个关键决策、质量属性、问题改进和总结；
- 至少覆盖性能、可用性、可维护性、安全中的三个属性；
- 每个关键决策都有替代方案、代价和验证；
- 全文不依赖代码，且逐段能标记事实、练习假设或设计建议；
- 自评连续两次 ≥60/100，并且扣题、权衡、问题改进三项均达到半数以上。

未通过时不要重新抄全文：先找出最低分的一项，重写对应 300～500 字；48 小时后重做同一题的提纲，7 天后写新题。若事实素材不足，使用定性结果，不要编造数字。

下一步进入总路线的 [综合冲刺](../soft-architect-study-roadmap.zh-CN.md#阶段-6第-40～42-周综合冲刺)，保持每周一套上午题和一套案例题。
