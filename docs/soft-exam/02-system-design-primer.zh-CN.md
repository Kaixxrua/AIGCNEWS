# 02｜System Design Primer 学习手册

> 资料： [System Design Primer 中文版](https://github.com/donnemartin/system-design-primer/blob/master/README-zh-Hans.md)。
>
> 用时：第 8～15 周，每周约 6～8 小时。
>
> 目的：训练“从需求和质量属性推导架构”的能力，不学习代码实现，也不把面试答案当成固定标准答案。

## 1. 学习边界和固定产出

只阅读中文 README 中的系统设计主题、图示和概念说明。跳过编程面试、代码资源、语言教程和完整实现。每个主题必须产出四件东西：

1. 一张组件图；
2. 一条请求或数据流；
3. 两项方案取舍；
4. 一个故障场景及恢复办法。

所有容量数字分三类：架构文档已确认的事实、题目给出的数字、自己明确写出的练习假设。AIGCNEWS 的未知吞吐量、SLA、成本和用户规模不可自行补齐。

## 2. 系统设计的固定答题顺序

遇到任何设计题，按以下顺序写，避免一上来罗列组件：

1. **澄清目标**：用户是谁，核心读写是什么，哪些功能不在范围；
2. **列约束**：延迟、吞吐、可用性、一致性、安全、成本和运维限制；
3. **画高层图**：客户端、边界、服务、存储、异步链路；
4. **定位瓶颈**：容量、单点、热点、慢查询、队列堆积或外部依赖；
5. **给方案**：先给最小可行方案，再给扩展路径；
6. **讲权衡**：每个关键选择说明收益、代价和适用条件；
7. **补故障闭环**：监控、超时、重试、降级、恢复和数据补偿；
8. **说明验证**：用什么指标、压测或演练确认方案有效。

## 4. 主题学习卡

### 4.1 性能与容量

**掌握**：延迟、吞吐量、并发、带宽、容量、峰值、平均值、排队。先分清“同时在线人数”和“单位时间请求数”，再估算最忙时段。

**不要求**：精确预测生产指标。考试中若无数字，写出公式、变量和假设即可。

**练习**：假设一个页面高峰每秒收到 100 个请求，每个请求平均读取 3 次数据库；不考虑缓存时，数据库读压力约为每秒 300 次。若缓存命中率假设为 80%，剩余数据库读约为每秒 60 次。这里的 100、3、80% 都是练习假设。

**取舍**：缓存可以降低数据库压力和延迟，但增加失效、脏读和内存成本；异步队列可以削峰，但会引入处理延迟和重复消费问题。

**AIGCNEWS**：首页读取可能使用 PostgreSQL 事实和 Redis 缓存；Milvus/Neo4j 用于派生检索。不要把架构中的组件数量当成性能证明。

**自测**：给定“延迟高、数据库慢、峰值突发”场景，写出三个可能瓶颈、两种缓解方案和每种代价。

**通过线**：15 分钟内完成，必须区分延迟与吞吐，并写出至少一个练习假设。

### 4.2 可用性、可靠性和可观测性

**掌握**：冗余、健康检查、超时、重试、熔断、降级、限流、日志、指标、追踪、恢复点。可靠性不仅是“多部署一台机器”，还包括数据恢复和运维闭环。

**常见误区**：无限重试会放大故障；只做重试不做超时会占满连接；监控有数据不等于有可执行告警。

**练习**：一个外部富化服务变慢时，系统如何保证用户仍能看到基础内容？

**参考结构**：设置连接和请求超时；隔离慢依赖；返回已持久化的基础结果；把富化改为异步重试；记录失败任务和告警；恢复后补处理。代价是结果暂时不完整、运维复杂度增加。

**AIGCNEWS**：多源采集采用单源失败隔离；派生索引可重建；订阅派发强调幂等。它们都是故障闭环的案例。

**自测**：画“依赖正常、依赖超时、依赖恢复”三态图，并标出用户可见结果。

**通过线**：图中有超时、降级、告警和恢复四个节点。

### 4.3 CAP、一致性与幂等

**掌握**：网络分区发生时，一致性与可用性存在取舍；CAP 不是任意时刻只能选两个；最终一致意味着允许暂时不同，但必须有收敛路径；幂等是重复执行得到相同业务结果的性质。

**练习**：为什么“事实主库写成功、向量索引稍后更新”可以采用最终一致？

**参考答案**：用户首先需要结构化事实可靠落库，向量索引属于可重建派生能力；写入和索引更新分离可以避免跨存储分布式事务，但短时间内搜索可能看不到新内容，因此需要重试、补建、状态记录和告警保证最终收敛。

**AIGCNEWS**：PostgreSQL 是事实主库，Redis/Milvus/Neo4j 是派生能力；当前架构没有分布式事务。

**自测**：分别说明“支付权益发放”“搜索索引更新”“用户收藏读取”更适合哪种一致性关注，并指出一个风险。

**通过线**：能说清至少两类业务为什么不能用同一套一致性策略，并说明幂等键/去重的作用。

### 4.4 DNS、CDN、负载均衡和反向代理

**掌握**：DNS 负责名字到地址的解析；CDN 缩短静态内容访问距离；负载均衡分配请求；反向代理位于客户端与后端之间，可承担 TLS、路由、限流和安全头。

**常见误区**：CDN 不能替代数据库；负载均衡不能自动解决共享状态；HTTPS 不能自动防止越权。

**练习**：画用户访问 AIGCNEWS 的边界路径，标出 TLS、nginx、API、SSE 和内部存储的职责。

**AIGCNEWS**：当前公网边界由 nginx 提供 TLS、反向代理、限流和 SSE 相关代理配置；独立 Go MCP 服务有明确路由边界。

**通过线**：图中至少有客户端、DNS/边缘、反向代理、应用、存储五类节点，并写出两个边界责任。

### 4.5 缓存与数据库

**掌握**：缓存旁路、读写穿透、失效策略、TTL、热点、缓存击穿/雪崩/穿透；关系数据库、索引、复制、分片、反规范化的适用条件。

**练习**：如果 Redis 不可用，怎样保证 AIGCNEWS 的核心事实仍可读取？

**参考答案**：将 PostgreSQL 作为事实来源；缓存读取失败时有限度回源并配合限流、超时和降级，避免大量请求同时击穿数据库；恢复后重新预热。代价是延迟上升和数据库压力增加。

**AIGCNEWS**：Redis 还承担 OTP、限流、访客去重等用途，不应简单说“Redis 只是缓存”；不同用途的故障策略不同。

**自测**：列出缓存失效的三种风险及各自一项控制措施。

**通过线**：至少答出 TTL/失效、回源保护、热点或雪崩中的三项，并说明代价。

### 4.6 消息队列、异步任务与背压

**掌握**：队列用于解耦、削峰、异步和重试；生产速度超过消费速度时需要背压、限流、扩容或丢弃低优先级任务；至少一次投递要求消费者幂等。

**练习**：采集完成后同时更新多个派生索引，如何避免一个慢索引阻塞主写入？

**参考结构**：先写 PostgreSQL，再记录待处理任务或事件；派生更新异步消费，失败重试并告警；消费者按唯一业务键幂等。代价是索引延迟和任务运维成本。

**AIGCNEWS**：采集、富化、快照、补采和派生索引天然具有异步边界；不要声称项目已使用某个队列，除非当前架构文档有依据。

**通过线**：图中有生产者、队列、消费者、重复消息处理和失败重试。

### 4.7 服务边界、微服务与安全

**掌握**：服务拆分应以领域边界、独立扩展、故障隔离和团队/部署需求为依据；模块化单体也可以有清晰边界。安全要同时考虑认证、授权、输入校验、密钥、审计、限流和 SSRF。

**练习**：为什么 AIGCNEWS 的 MCP 入站可以由独立 Go 服务承载，而不代表所有模块都应该拆成独立服务？

**参考答案**：MCP 有独立协议、边界、限流和部署生命周期，独立承载有助于契约隔离和按需扩展；但拆分会增加网络调用、部署、观测和数据一致性成本，其他领域若没有独立边界则保留模块化结构更简单。

**AIGCNEWS**：`/api/mcp` 是独立 Go 服务；网站配置页和 Token 管理由登录保护；外部 URL 有 SSRF 策略。

**通过线**：必须写出拆分收益、至少两项代价、认证与授权的区别。

## 5. 综合白板题

### 题目：设计一个“多源内容聚合与搜索系统”

**练习约束**（均为题设假设）：

- 多个来源可能单独失败；
- 用户既要看最新榜单，也要搜索历史内容；
- 搜索索引允许短暂延迟，但最终必须收敛；
- 外部访问必须经过统一安全边界；
- 需要支持流式输出，但不能让代理无限缓冲。

**答题要求**：90 分钟完成一张架构图和 800～1200 字说明，至少覆盖采集隔离、事实主库、缓存/索引、流式边界、认证授权、重试补偿和监控告警。

**参考答案骨架**：

```text
数据源 → 单源采集器/任务记录 → 标准化 → 事实主库
                                  ├→ 缓存
                                  ├→ 向量/图派生索引
                                  └→ 异步富化与补采
客户端 → DNS/边缘反代 → API/SSE/MCP 边界 → 查询与消费层
```

说明主库与派生索引的一致性取舍；单源失败不阻断其他源；对外部依赖设置超时、重试、降级；对重复任务使用幂等键；对 SSE 关闭代理缓冲并设置合理超时；认证解决“是谁”，授权解决“能做什么”；用成功率、延迟、队列积压、索引滞后和错误率观测。

**评分 rubric（100 分）**：约束和范围 15 分；结构图 20 分；数据/一致性 20 分；性能与扩展 15 分；故障闭环 15 分；安全与观测 15 分。达到 60 分才算通过。

## 6. 第 15 周阶段验收

1. 在 90 分钟内完成上面的综合题或一套等难度题；
2. 解释 CAP、最终一致、缓存失效、队列背压、反向代理和服务边界；
3. 对 AIGCNEWS 说清 PostgreSQL、Redis、Milvus、Neo4j、nginx、MCP-Go、APScheduler 的职责；
4. 每个关键选择至少给出一个替代方案和代价；
5. 图中必须有数据流、请求流、故障流和恢复流。

**通过线**：8 道设计练习中至少 6 道满足“约束—方案—取舍—故障—验证”结构；综合题 ≥60/100。未通过时，按失分最多的一个维度回看对应章节，48 小时后重做同一题，不要重学全部内容。
